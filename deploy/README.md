# Деплой і експлуатація

Усе нижче виконується з каталогу проєкту на сервері. Стек описаний у
`compose.prod.yaml`, образ збирає CI і кладе в GHCR.

## Розкладка

| Що | Де |
|---|---|
| Проєкт | `/srv/flowers` |
| Секрети | `/srv/flowers/.env`, режим `600`, у репозиторії його немає |
| Бекапи | `/srv/backups/{db,media}` |
| Публічні медіа | том `flowers_media_public`, nginx роздає з `/srv/media-public` |
| Оригінали фото | том `flowers_media_private`, у контейнер nginx **не монтується** |
| Логи | json-file, ротація 10 МБ × 5 файлів на сервіс |

## Деплой

Мердж у `main` запускає `.github/workflows/deploy.yml`: збирає образ, штовхає
його в GHCR і виконує на сервері

```sh
./deploy/deploy.sh ghcr.io/<owner>/flowers:<sha>
```

Порядок кроків усередині — той, якого вимагає розділ 5 ядра: **міграції
доходять до кінця раніше, ніж щось перезапускається**, тому новий код ніколи не
зустрічає стару схему.

Ручних кроків немає. Після перезапуску відпрацьовує `deploy/smoke.sh`.

## Відкат

Одна команда з попереднім тегом:

```sh
./deploy/deploy.sh ghcr.io/<owner>/flowers:<попередній sha>
```

Теги образів — це sha комітів, список видно в GHCR або в `git log`. Якщо
відкат потрібен через міграцію, спершу відкотіть міграцію
(`python manage.py migrate <app> <номер>`), і тільки потім образ.

## Бекапи

`deploy/backup.sh` знімає `pg_dump` у власному форматі, пакує обидва медіа-томи
і видаляє все, старше за `KEEP_DAYS` (типово 14). Cron:

```
15 3 * * * cd /srv/flowers && ./deploy/backup.sh >> /var/log/flowers-backup.log 2>&1
```

Падіння будь-якого кроку йде в Telegram тим самим ботом, що й заявки. Тиша —
саме те, що робить зламаний бекап дорогим.

## Відновлення

Перевіряти на чистій машині, не на бойовій.

```sh
# 1. Підняти порожній стек
docker compose -f compose.prod.yaml up -d db redis

# 2. Залити дамп
gunzip -c /srv/backups/db/flowers-<stamp>.dump.gz \
  | docker compose -f compose.prod.yaml exec -T db \
      pg_restore --username flowers --dbname flowers --clean --if-exists

# 3. Повернути медіа
for volume in media_public media_private; do
  docker run --rm \
    -v "flowers_${volume}:/data" \
    -v /srv/backups/media:/backup \
    alpine:3 \
    sh -c "rm -rf /data/* && tar xzf /backup/${volume}-<stamp>.tar.gz -C /data"
done

# 4. Підняти решту і перевірити
docker compose -f compose.prod.yaml up -d
./deploy/smoke.sh https://<домен>
```

### Журнал перевірок відновлення

Розділ 14.3 вимагає, щоб відновлення було перевірене руками хоча б раз і
записане тут. Рядок дописується після кожної перевірки.

| Дата | Хто | Звідки брали | Результат |
|---|---|---|---|
| _не проводилась_ | — | — | **Перевірити до запуску.** Пункт чек-листа розділу 20. |

## Чек-лист перед запуском (розділ 22, S4-6)

Позначати можна прямо тут, у коміті.

- [ ] `DEBUG=False`, `ALLOWED_HOSTS` заповнений реальним доменом, `SECRET_KEY`
      унікальний і не з `.env.example`
- [ ] **`IP_HASH_SALT` замінений на унікальне значення.** Заглушка з
      `.env.example` робить хеш IP оборотним перебором
- [ ] HTTPS примусовий, HSTS увімкнений, куки secure — це вмикається саме
      значенням `DEBUG=False`, перевірити заголовки запитом
- [ ] пароль адміністратора надійний, `/admin/` за обмеженням по IP або з
      двофакторною автентифікацією
- [ ] `media-private` не роздається: `curl -I https://<домен>/media/works/...`
      повертає 404 (входить у `deploy/smoke.sh`)
- [ ] бекапи працюють за розкладом, відновлення перевірене і записане в
      журнал вище
- [ ] Telegram-бот підключений, тестова заявка дійшла
- [ ] Turnstile увімкнений з реальними ключами
- [ ] задача `core.ping` прибрана з коду (зроблено, є тест)
- [ ] `sitemap.xml` надісланий у Google Search Console
- [ ] аналітика збирає події після згоди: натиснути «Прийняти» і побачити
      `phone_click` у GA4
- [ ] перевірено на живому телефоні: iOS Safari і Android Chrome
- [ ] власник сам додав тестову роботу з чотирма фото і опублікував її
- [ ] власник знає, де вмикати банер і режим «не приймаємо замовлення»
- [ ] політика конфіденційності заповнена реальними даними, а не текстом із сіду
- [ ] контакти, години роботи й адреса збігаються з дійсністю

## Що дивитись, коли щось не так

```sh
docker compose -f compose.prod.yaml ps
docker compose -f compose.prod.yaml logs -f web celery
curl -sS https://<домен>/healthz/   # {"status": "ok", "database": "ok", "cache": "ok"}
```

`/healthz/` відповідає 503, якщо не дістає Postgres або Redis. Сайт при цьому
може працювати: недоступний Redis деградує до прямого читання, а не до
помилки.
